# Advanced RAG 3단계 — 학사일정 구조화

- 작성일: 2026-11-26
- 작업 브랜치: feat/advanced-rag-stage3-1126
- 대상: 학교 홈페이지 대학 학사일정(11360)

## 1. 작업 목적

기존 학사일정 문서 조각을 구조화하여
이후 검색 및 답변 단계에서 날짜와 학년도를
명확하게 구분할 수 있도록 한다.

기존 수집 방식과 검색 데이터는 변경하지 않는다.

## 2. 공식 출처

https://www.hufs.ac.kr/hufs/11360/subview.do

원본: data/chunks.json

대상 조각:
- 11360-01
- 11360-02
- 11360-03
- 11360-04

수집된 2026학년도 학사일정을 사용한다.
학교 홈페이지의 실시간 변경 사항을
자동 반영하는 기능은 아니다.

## 4. 데이터 구조

shared/academicCalendar.js

ACADEMIC_CALENDAR:
- academicYear: 일정표의 학년도
- sourceHash: 학사일정 조각 4개의 SHA-256
- items: 구조화된 일정 목록

개별 일정 필드:
- id: 원문 조각 및 행 순서 기반 ID
- academicYear: 원문 일정표 학년도
- period: 원문 조각의 구역
- targetSemester: 일정의 실제 적용 학기 또는 null
- name: 원문 일정명
- startDate: 시작 날짜(YYYY-MM-DD)
- endDate: 종료 날짜 또는 null
- sourceId: 기존 검색 조각 ID
- sourceUrl: 학교 공식 출처
- collectedAt: 원본 수집 시각

period는 수집 조각의 구역이며
실제 행사의 적용 학기를 확정하는 값은 아니다.

### 해당 학기 분류 (11/26 PM 리뷰 반영)

targetSemester와 period를 별도로 관리한다.

| 일정 | period | targetSemester |
|---|---|---|
| 2026년 8월 10일 수강신청 | summer | 2026-2 |
| 2027년 2월 10일 수강신청 | winter | 2027-1 |
| 2027년 2월 22일 수강신청 | winter | 2027-1 |
| 2026년 12월~2027년 1월 성적 정정 | fall | 2026-2 |

분류 원칙:

- 정규학기는 YYYY-1 또는 YYYY-2 형식을 사용한다.
- 하계 계절학기는 YYYY-summer로 분리한다.
- 동계 계절학기는 YYYY-winter로 분리한다.
- 동계 계절학기의 연도는 원문 일정표 학년도를 사용한다.
- 방학 중 다음 정규학기 수강신청과 휴복학은 적용 학기로 분류한다.
- 후기 졸업은 해당 학년도 1학기에 연결한다.
- 다음 해 전기 졸업은 해당 학년도 2학기에 연결한다.
- 독립 공휴일 및 분류 근거가 부족한 일정은 null로 유지한다.

위 분류는 원문 일정명과 구역을 기반으로 만든 파생 정보다.
학교가 별도로 제공한 학기 식별자는 아니다.

기존 학년도, 일정명, 시작일, 종료일,
출처 및 수집일은 변경하지 않는다.

현재 학사일정 63개에 targetSemester 필드를 추가하였다.
다음 학년도 원문 갱신 시 새로운 일정명과 분류 결과를 검토한다.

검색 API에서 사용할 때는 null을 특정 학기로 간주하지 않는다.
계절학기와 정규학기도 서로 구분한다.

## 5. 날짜 처리 원칙

- 2026학년도 범위는 2026년 3월부터
  2027년 2월까지다.
- 2027년 1~2월의 실제 연도를 보존한다.
- 연도를 넘기는 일정의 시작일과 종료일을 보존한다.
- 단일 날짜 일정의 종료일은 null로 유지한다.
- 원문에 없는 날짜와 시간은 생성하지 않는다.
- 잘못된 날짜, 역전된 기간, 학년도 범위 밖 날짜는
  구조화 과정에서 차단한다.

2027학년도 제1학기 개강일은 (11/26 기준)
현재 수집된 일정표에 없다. → 11/27 2027학년도 화면을 수집해 해소(10장).

2026년 3월 1일, 2일, 3일의
학기개시일 및 개강 관련 기록은 모두 보존한다.

원문에서 분리되거나 복합적으로 작성된 일정명도
임의로 합치거나 변경하지 않는다.

## 6. 실행 방법

최초 생성:

    npm run calendar

원문과 생성 데이터 일치 여부 확인:

    npm run calendar -- --check

명시적 갱신:

    npm run calendar -- --update

기존 파일이 존재하면 기본 생성 명령은 실패한다.
--update는 기존 생성 파일이 있을 때만 허용한다.

원문 구조 검증에 실패하면 생성 또는 갱신하지 않는다.
동일한 원문에서 동일한 결과를 생성한다.

## 7. 갱신 절차

1. 학교 공식 학사일정 변경 여부 확인
2. 팀 승인 후 공식 원문 재수집
3. 일정명, 날짜, 학년도 검토
4. npm run calendar -- --update
5. npm run calendar -- --check
6. 변경된 생성 파일 및 회귀 테스트 검토
7. npm test
8. npm run build

기존 실서비스 데이터 수집 및 DB 저장 작업은
별도의 팀 운영 절차에 따른다.

## 9. 제한 및 후속 작업

- 현재 구조화 데이터는 수집된 원문 기준이다.

### 10.2 학사일정 바로 찾기 규칙 (`shared/calendarRoute.js`, 동의어 표 `shared/calendarTerms.js`)

검색창(`api/ask.js`)이 검색하기 전에 한 번 확인한다. 오늘 날짜는 한국 날짜(`kstToday`)다.

1. **날짜 질문 판별**: 질문에 날짜를 묻는 말이 있고(언제 · 며칠 · 날짜 · 일정 · 기간은/이 · 마감 · ○○일 · 시작 · 끝나 · when · date · deadline …), 동의어 표 항목 하나와 맞을 때만 한다.
   - 항목: 사전수강신청 · 수강신청 변경 · 수강신청 취소 · 수강신청 · 중간 · 기말 · 보강 · 휴복학 · 성적 열람/정정 · 학위수여식 · 계절학기 · 개강 · 종강
   - 구체적인 일정 표현부터 확인하고 중복 표현을 제외한다. 서로 다른 일정이 두 개 이상이면 일반 검색으로 넘긴다. 단, 계절학기 개강 또는 종강은 하나의 일정으로 처리한다.
   - "수강신청 변경 기간에 …"처럼 "기간에"는 날짜를 묻는 말로 보지 않는다.
   - **바로 찾기를 건너뛰는 질문(11/27 PM 결정)**: 날짜 말고 다른 것을 같이 물으면 지금처럼 검색만 한다(`OTHER_INTENT`).
     - 판단 단어: 성적(단, "성적 열람 · 정정 · 확인 · 이의"는 일정 이름이라 제외), 학점, 방법, 어떻게, 어디, 장소, 위치, 대상, 자격, 조건, 서류, 준비물, 제출, 절차, 비용, 금액, 등록금, 누가, 누구, 몇 명, 인원
     - 영어: how, where, who, eligib…, requirement, document, fee(s), grade(s)(단, grade check · correction · appeal 제외), credit(s)
   - **계절학기만 말한 질문**: "계절학기"를 말했으면 여름 · 겨울 없이도 계절학기 학기만 후보로 본다. 그 일정이 학사일정에 없으면(예: 계절학기 수강신청) 바로 찾기를 하지 않는다.
   - **날짜 질문 넓히기**: 며칠, 몇 일 · 몇일, 몇 월, 날짜, 일자, 일정, 기간은 · 이, 마감, ○○일(개강 · 개학 · 종강 · 시작 · 마감 · 신청 · 종료), 시작해 · 시작돼, 끝나, 언제(언제부터 · 언제까지 포함), when, what date · day, date(s), deadline, period, schedule
   - **일정 이름의 다른 말**(학사일정 일정 이름에 정확히 대응하는 것만)
     - 졸업식 → 학위수여식
     - 개학 · 학기 시작 → 개강
     - 중간고사 · 중간평가 → 중간시험
     - 기말고사 · 기말평가 · final exam → 기말시험
     - 수강정정 · 수강 변경 → 수강신청 변경
     - 수강철회 · 수강 취소 → 수강신청 취소
     - 휴학 신청 · 복학 신청 → 휴 · 복학 신청
     - 성적 확인 · 이의 → 성적 열람 및 정정
     - "예비수강신청"(관심강좌 담기)은 사전수강신청과 다른 제도라 넣지 않는다(11/27 동의어 표에서 뺌).
   - 전기·후기 학위수여식은 질문에 명시된 구분과 일치하는 일정만 후보로 둔다. 두 종류를 함께 물으면 일반 검색으로 넘긴다.
2. **대상 학기**
   - 질문에 학년도 · 학기가 있으면 그대로 쓴다: "2027학년도 1학기", "2027년 1학기", "이번 · 다음 · 지난 학기", "여름 · 겨울 계절학기", "2026 Spring", "Summer session".
   - 연도 없이 "1학기" · "2학기"만 있으면 아직 끝나지 않은 가장 가까운 그 학기로 한다. 1학기는 3~8월, 2학기는 9월~다음 해 2월까지로 본다.
   - 연도만 있으면("2027학년도 개강일") 그 학년도의 학기 안에서 아래 방식 B로 고른다. 그 학년도에 그 일정이 없으면 바로 찾기를 하지 않는다. 미수집 학년도의 정규학기 개강·종강 질문은 10.5절의 범위 검사를 적용한다.
   - **학년도 vs 달력 연도(11/27 PM 확정)**: 학교 일정표는 학년도(3월~다음 해 2월) 단위지만, 일정 이름과 날짜는 달력 연도를 쓴다(예: 2026학년도 안의 "2027년 전기 학위수여식" = 2027.02). 그래서 질문의 연도를 아래처럼 나눠 읽는다.
     - "YYYY학년도"는 그 학년도다(지금과 같음).
     - "YYYY년 N학기"는 YYYY학년도 N학기다.
     - "YYYY년 M월"은 달력 날짜다. 1~2월이면 (YYYY-1)학년도, 3~12월이면 YYYY학년도 안에서, 실제 날짜가 그 달에 걸치는 일정만 후보로 둔다. 그런 일정이 없으면 일반 검색으로 넘긴다. 단, 계절학기 일정에 한해 그 달을 포함하는 학기의 일정을 쓴다(예: "2027년 1월 겨울 계절학기 시작" → 2026학년도 겨울 계절학기 12/22 개강).
     - "YYYY년"(월 · 학기 없음)은 시작일이나 종료일이 YYYY년인 일정만 후보로 두고 방식 B로 고른다. 없으면 바로 찾기를 하지 않는다.
     - 달력 연도로 물은 질문도 연도가 분명하므로 termBasis · 버튼을 붙이지 않는다.
     - 예: "2028년 2월 학위수여식 언제야?" → 2027학년도 · 2028.02.18. "2027년 8월 후기 학위수여식 언제야?" → 2027학년도 · 2027.08.20.
   - 학기 말이 없으면(방식 B): 그 항목이 있는 학기 중 일정이 오늘 이후에 끝나는 가장 가까운 학기를 고른다.
   - 방식 B로 하나를 못 정하면(후보 일정이 모두 지났거나, 같은 날짜의 후보 학기가 둘 이상) **clarify(방식 A)**: AI를 부르지 않고 학기 버튼만 돌려준다.
3. **근거**: 그 학기의 맞는 일정 줄을 모두 하나의 자료로 묶어 **근거 1순위**로 넣는다. 나머지 검색은 지금처럼 이어서 한다.
   - 형식: `[학사일정 바로 찾기] 2027학년도 제1학기 > 2027.02.10 ~ 2027.02.12: 수강신청(2~4학년)`
   - 출처 링크는 11360 화면(2027학년도 일정은 `?year=2027`)이다.
   - 원문 보여 주기(evidence)로 넘어가도 이 자료가 맨 앞이다.
4. **응답 칸**
   - 다른 학기 버튼 규칙(11/27 PM 확정)
     - 학기가 분명한 질문(연도+학기, "이번 · 다음 · 지난 학기")에는 `termBasis` · `alternatives`를 모두 붙이지 않는다.
     - 그 밖에는 `termBasis: { semester, label, labelEn }`를 붙인다.
   - `alternatives: [{ semester, label, labelEn, question }]`는 **1개**다.
     - 기본 답 다음에 오는 같은 항목(질문이 1학기 · 2학기 · 계절학기처럼 종류를 말했으면 같은 종류 중 다음 것)을 고른다.
     - 다음 것이 데이터에 없으면 바로 전 것, 둘 다 없으면 없음.
     - 학기 순서는 그 학기 일정의 가장 이른 시작일로 정한다.
     - clarify일 때만 오늘과 가까운 학기 최대 2개를 버튼으로 준다.
   - 근거 줄의 일정이 오늘 이전에 끝났으면 줄 끝에 "(오늘 기준 지난 일정)"을 붙인다. 이미 지났다는 것을 답에 말할 수 있게 하려는 것이다.
   - 답변 생성: 바로 찾기를 한 질문에만 질문 뒤에 한 줄을 덧붙인다(`calendarNote`). 다른 질문의 지시문은 그대로다.
     - 덧붙이는 줄: "[학사일정 기준] 이 질문은 ○○ 일정을 묻는 것으로 본다. [1] 학사일정 바로 찾기 자료의 날짜로 답하고, 다른 학기 · 연도의 날짜로 대신하지 않는다. 이미 지났으면 지났다고 말한다."
     - 11/27 Preview D3 · D4 · D8에서 다른 학기 수강신청 안내 · 휴학 규정의 날짜로 답한 문제에 대한 대응이다.
   - 서버 검사(`answerHasRouteDate`): 인식된 날짜가 하나도 없거나 인식된 날짜 중 하나라도 바로 찾기 일정과 일치하지 않으면 원문 보여 주기(evidence)로 넘긴다. 명시된 연도도 비교하며, 연도가 생략된 날짜는 월·일을 비교한다.
     - 이때는 그 학기 일정 줄만 보여 주고, 로그 reason은 `calendar_mismatch`다.
     - 근거에 없는 날짜 검사(guard)보다 먼저 확인한다.
     - question은 원 질문의 학기 말을 그 학기 이름으로 바꾼 문장이다. 영어 질문이면 "2027 Spring: …"처럼 앞에 붙인다.
   - clarify면 `{ mode: "clarify", clarify: true, answer: null, sources: [], alternatives }`.
5. **바뀌지 않는 것**
   - 날짜 질문이 아니거나 맞는 일정이 없으면 일반 검색을 유지한다(응답에 새 칸 없음). 단, 10.5절의 미수집 학년도 개강·종강 질문은 제외한다.
   - 바로 찾기를 한 질문과 미수집 학년도 범위 검사에 걸린 질문은 답변 캐시를 쓰지 않는다.
   - 학사일정 관련 로그에는 `calendar`(route/clarify), `calendarTopic`, `calendarSemester`를 남긴다. 미수집 학년도 차단은 `reason: calendar_unavailable`로 기록하며 질문 · 답 내용은 남기지 않는다.
6. **화면**(`src/scenes/DialogScene.js`, 문구 `src/state.js`)
   - termBasis가 있으면 답 아래에 작은 글씨로 "2027학년도 1학기 기준으로 답했어요"를 보여 준다(영어 "Answered for 2027 Spring (1st semester)").
   - alternatives는 "2026학년도 1학기 일정 보기" 버튼으로 보여 주고, 누르면 그 question으로 다시 묻는다.
   - clarify면 "어느 학기 일정을 찾으세요?"(영어 "Which semester?")와 버튼만 보여 준다.
