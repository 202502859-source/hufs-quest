# 💾 로그인 · 진행 저장 API 합의안

> 이종헌(게임 화면)과 임현규(서버·DB)가 같은 약속을 보고 따로 작업하기 위한 문서입니다.
> **이 문서의 응답 형식이 확정되면, 서버가 완성되기 전에도 화면 쪽은 가짜 응답으로 먼저 개발합니다.**
> 상태: **확정 (2026-11-17)** · 바꿀 일이 생기면 이 문서를 PR로 고치고 아래 결정 사항 표에 기록합니다.

## 1. 지금 상태 (코드 기준)

| 데이터 | 위치 | 지금 방식 | 바꿀 방향 |
| --- | --- | --- | --- |
| 로그인 모드(재학생/게스트) | `src/state.js` `session.mode` | 버튼만 누르면 재학생, 실제 로그인 없음 | 학교 이메일 로그인 |
| 레벨 · 경험치 · 포인트 | `session.level`, `exp`, `expMax`(100), `points` | 메모리, 시작 값은 시연용 가짜(Lv.3, 120점) | 서버 저장, 새 계정은 0부터 |

| 퀴즈 기록 | `src/quizProgress.js` `progress` | 메모리, 경험치 지급·하루 상한(50)을 **브라우저가 계산** | **서버가 계산** |
| 안내 중 퀘스트, 받은 보상 알림 | `session.trackedQuest`, `pendingReward` | 메모리 | 그대로 화면에만 둠 (저장 안 함) |

## 2. 핵심 원칙

1. **화면은 "무슨 일이 있었는지"만 보내고, 보상은 서버가 정한다.**
   화면이 "경험치 10 더해 줘"라고 보내면 누구나 조작할 수 있습니다. 화면은 "퀴즈 seasonal-credits에 X를 골랐다"만 보내고, 정답 확인 · 중복 지급 확인 · 하루 상한 · 경험치 계산은 모두 서버가 합니다.
2. **게스트는 지금처럼 메모리에서만 동작한다.** 게스트는 API를 부르지 않습니다.
3. **서버 응답에는 항상 최신 진행 상태 전체를 담는다.** 화면은 응답을 받으면 그 값으로 `session`을 덮어쓰기만 하면 됩니다. 화면에서 따로 더하고 빼지 않습니다.
4. **API 키는 서버에만 있다.** 화면은 로그인 토큰만 들고 `Authorization: Bearer <토큰>`으로 보냅니다.
5. **하루 기준은 한국 시간(Asia/Seoul) 자정.** 지금은 기기 시간 기준이라 서버에서 통일합니다.

| 항목 | 구현 내용 |
| --- | --- |
| 방식 | Supabase Auth **이메일 인증 코드(6자리)** 로그인. 비밀번호 없음. `signInWithOtp`(`shouldCreateUser: true`)로 보내고 `verifyOtp`(`type: "email"`)로 확인 |
| 입력 | **학교 메일 아이디 + 도메인 목록**. 목록은 지금 `@hufs.ac.kr` 하나(`src/data/authRules.js`의 `EMAIL_DOMAINS`). 이메일은 코드에서 "아이디 + 선택한 도메인"으로만 조립 |
| 아이디 규칙 | **영문 대 · 소문자와 숫자, 최대 64자**(`MAIL_ID_MAX_LENGTH`. 구글 상한이며 학교 공식 상한은 확인 못 함). 마침표 · 밑줄 · 하이픈 등 다른 글자는 입력 즉시 지움. 입력칸에는 친 그대로 보여 주고, **보낼 때 소문자로 변환**(`buildEmail`. Supabase는 이메일을 소문자로 저장하고 구글 메일은 대 · 소문자를 구분하지 않아 같은 계정이 둘로 나뉘지 않게). 9자리 학번 아이디도 그대로 통과. "아이디@hufs.ac.kr" 전체를 붙여 넣으면 아이디만 남기고 드롭다운을 맞추며, 목록에 없는 도메인이면 "학교 메일(@hufs.ac.kr)만 사용할 수 있어요"로 막음 |
| 규칙 근거 | 학교 메일 아이디는 영문(대 · 소문자)과 숫자만 쓸 수 있고, 학번만이 아니라 학생이 직접 정할 수 있음. HUFS 메일은 Google Workspace 기반이라 길이 상한은 구글 기준(64자)을 따름 |
| 허용 주소 | `@hufs.ac.kr`만. 화면 제한은 우회할 수 있으므로 서버에서 두 번 막음: Supabase Auth Hook(Before User Created)이 다른 도메인 가입 거절, 진행 API는 다른 도메인 토큰에 `403` |
| 코드 규칙 | 숫자 6자리, 붙여넣기 가능, 6자리가 차면 자동 확인. **만료 10분**(대시보드 Email OTP Expiration 600초와 같게), **같은 주소 재발송은 60초 뒤**(남은 초 표시) |
| 틀림 · 만료 | "인증 코드가 맞지 않아요" / "인증 코드가 만료됐어요. 다시 받아 주세요". Supabase는 둘을 같은 오류로 돌려주므로 화면이 코드를 보낸 시각으로 구분 |
| 화면 흐름 | 타이틀 "재학생 로그인" → 학교 메일 아이디 + 도메인 → "인증 코드 받기" → 6자리 코드 → `GET /api/progress` → `POST /api/check-in` → 캠퍼스 입장. "아이디 다시 입력"으로 돌아가기, Esc로 닫기 |
| 토큰 보관 | Supabase JS 클라이언트가 브라우저에 보관(새로고침해도 로그인 유지, 로그인 창 없이 바로 진행 불러오기). 진행 API가 `401`이면 로그인을 지우고 로그인 창을 다시 엶 |
| 로그아웃 | HUD 상태창 안 "로그아웃" 버튼(재학생만) → 타이틀로 |
| 개인 정보 | 메일 아이디 · 이메일은 브라우저 메모리에만 잠깐 두고 콘솔 · 오류 메시지 · 저장소에 남기지 않음 |
| 모드 | 로그인 `VITE_AUTH_MODE`, 진행 저장 `VITE_PROGRESS_MODE`를 **따로** 고름. 둘 다 기본값 `mock`. 가짜 로그인은 메일 없이 화면 구석에 개발용 코드를 보여 줌(`?mockotp=fast`면 20초 뒤 만료). "진짜 로그인 + 가짜 진행 저장"으로 로그인만 먼저 시험 가능. 가짜 로그인 + 진짜 진행 저장이면 진짜 토큰이 없으므로 콘솔 경고 후 진행 저장도 `mock` |
| 공개 키 | 브라우저에는 Supabase URL과 Publishable(anon) 키만(`VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`). 서버 비밀 키는 브라우저 금지. 모든 public 테이블 RLS 켜짐 확인(2026-11-18) |

인증 링크 대신 6자리 코드를 쓰는 이유: 링크 방식은 메일 앱에서 누르면 다른 브라우저가 열려 로그인이 안 되는 경우가 많고, 발표장에서 시연하기도 불편합니다.

## 4. API

모든 요청은 `Content-Type: application/json`, 재학생 요청은 `Authorization: Bearer <토큰>`을 붙입니다.

### 공통 응답: 진행 상태 (`progress`)

```json
{
  "level": 1,
  "exp": 30,
  "expMax": 100,
  "points": 0,
  "completedQuests": ["doubleMajor"],
  "quiz": {
    "rewarded": ["seasonal-credits", "warning-dismissal", "grad-2025"],
    "answered": ["seasonal-credits", "warning-dismissal", "grad-2025", "minor-credits"],
    "todayExp": 30,
    "dailyCap": 50
  }
}
```

- `level`, `exp`는 서버가 누적 경험치(`total_exp`)에서 계산해서 줍니다. 계산식: `level = floor(total_exp / 100) + 1`, `exp = total_exp % 100`. 지금 화면의 `gainExp`와 같은 결과입니다.
- `quiz.answered`는 다음 상자에 아직 안 푼 문제를 먼저 내는 데 씁니다. 순서는 처음 푼 순서입니다.

### ① `GET /api/progress` — 진행 상태 불러오기

로그인 직후, 그리고 새로고침했을 때 한 번 부릅니다.

| 응답 | 내용 |
| --- | --- |
| `200` | `{ "progress": { … } }` 처음 로그인한 사용자면 서버가 0으로 새로 만듦 |
| `401` | 로그인 안 됨 / 토큰 만료 → 화면은 타이틀로 돌아감 |
| `403` | `@hufs.ac.kr`이 아닌 계정 |

### ② `POST /api/quiz-answer` — 퀴즈 답 기록

```json
{ "questionId": "seasonal-credits", "choice": false }
```
`choice`는 사용자가 고른 답(O = `true`, X = `false`)입니다. **정답 여부는 서버가 `src/data/quiz.js`와 비교해서 판단합니다.**

```json
{ "result": "ok", "correct": true, "gained": { "exp": 10, "points": 0 }, "leveledUp": false, "progress": { … } }
```

`result` 값은 지금 `recordAnswer()`가 돌려주는 값과 같습니다. 화면 메시지를 그대로 다시 쓸 수 있습니다.

| `result` | 뜻 | 화면 메시지 (`state.js`) |
| --- | --- | --- |
| `ok` | 정답, 경험치 지급 | `quizCorrect` |
| `wrong` | 오답 | `quizWrong` |
| `already` | 이미 경험치를 받은 문제 | `quizAlready` |
| `cap` | 오늘 상한(50) 도달 | `quizCap` |

`400`: 없는 문제 ID · `429`: 요청이 너무 잦음

### ③ `POST /api/quest-complete` — 퀘스트 완료 기록

```json
{ "questId": "doubleMajor" }
```
```json
{ "result": "ok", "gained": { "exp": 10, "points": 10 }, "leveledUp": false, "progress": { … } }
```
- 서버는 허용된 퀘스트 ID 목록에 있는지만 확인합니다. 보상은 `shared/progressRules.js`에서 정합니다(퀘스트마다 경험치 10, 포인트 10).
- 이미 완료한 퀘스트면 `"result": "already"`, 보상 없음.
- 범위 밖 기능인 `mockReg`(모의 수강신청)는 목록에 넣지 않습니다.

### ④ `POST /api/check-in` — 하루 첫 접속 보상

로그인 직후 `GET /api/progress` 다음에 한 번 부릅니다. 요청 본문은 없습니다.

```json
{ "result": "ok", "gained": { "exp": 0, "points": 5 }, "progress": { … } }
```
- 한국 시간 기준 하루에 한 번만 지급합니다. 오늘 이미 받았으면 `"result": "already"`.
- `GET /api/progress`에서 보상까지 주지 않고 따로 나눈 이유: 불러오기는 몇 번을 불러도 결과가 같아야 오류 처리와 재시도가 쉽습니다.
- 화면은 `ok`일 때만 "출석 보상 +5 포인트" 같은 알림을 띄웁니다.

### 행사 참여 보상 (나중에)

행사 기능을 만들 때 `POST /api/event-join` 같은 API를 추가합니다. **참여를 어떻게 확인할지**(예: 행사 부스의 QR 코드 스캔)를 그때 정해야 해서, 이번 범위에서는 아래 `reward_log` 테이블에 기록할 자리만 만들어 둡니다.

## 5. 데이터베이스 (Supabase, 임현규)

SQL은 `supabase/` 폴더에 저장합니다.

| 테이블 | 열 | 비고 |
| --- | --- | --- |
| `profiles` | `user_id`(PK, auth.users 참조), `email`, `total_exp`, `points`, `created_at`, `updated_at` | 첫 `GET /api/progress` 때 생성 |
| `quiz_log` | `user_id`, `question_id`, `correct`, `rewarded`, `answered_at`, `rewarded_at` · PK(`user_id`, `question_id`) | 하루 경험치는 `rewarded_at`이 오늘(한국 시간)인 행으로 계산 |
| `quest_log` | `user_id`, `quest_id`, `completed_at` · PK(`user_id`, `quest_id`) | |
| `reward_log` | `user_id`, `source`, `ref_id`, `exp`, `points`, `created_at` · UNIQUE(`user_id`, `source`, `ref_id`) | 모든 보상 지급 기록. `source`: `quiz` · `quest` · `check-in` · `event` · 앞으로 추가될 것. 출석은 `ref_id`에 날짜(`2026-11-19`)를 넣어 하루 한 번을 DB가 보장 |

`reward_log`를 따로 두는 이유: 포인트를 얻는 방법이 앞으로 더 늘어날 예정이라, 새 방법이 생겨도 `source` 이름만 하나 추가하면 됩니다. 같은 보상이 두 번 들어가는 것도 UNIQUE 조건이 막아 줍니다. `profiles`의 `total_exp`, `points`는 이 기록을 더한 값과 항상 같아야 합니다.

- 모든 테이블에 **RLS(행 단위 보안)를 켜고**, 쓰기는 서버 함수(서비스 키)만 합니다. 브라우저가 Supabase 테이블에 직접 쓰지 않습니다.
- 경험치 지급과 기록 저장은 **한 번에 같이** 처리합니다(둘 중 하나만 저장되는 일이 없게).
- 행사 테이블은 이 문서 범위 밖입니다. 행사 기능을 할 때 따로 정합니다.
